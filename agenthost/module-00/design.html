Two audiences, different priorities

Enterprise optimizes for trust. Consumer optimizes for flow.

B2B

Enterprise / Business

Named agent instances for internal teams and multi-tenant platforms.

  • Strict tenant and department boundaries
  • Entra ID, RBAC, Conditional Access
  • Auditability, private networking, data residency
  • Predictable capacity and SLA
Security - Governance - Reliability
B2C

Consumer / End-user

High-volume, often short-lived sessions for users, teams, and playgrounds.

  • Fast activation and simple operations
  • User-level sandbox isolation
  • External identity or API-driven access
  • Aggressive scale-to-zero and pay-per-use
Cost - Speed - Simplicity

Key Technical Considerations - Stateful design

Persist first. Then hibernate safely.

1

Start

Resolve the agent ID and load its JSON state from Blob.

2

Act

Handle messages, tools, and governed model calls.

3

Save

Write conversation and tool state after every change.

4

Idle

Evict, pause, or scale to zero without a final flush.

5

Resume

Restore directly from the latest durable Blob version.

Single source of truth: <AGENT_ID>.json in Blob Cool tier with versioning. No separate Redis hot cache.

Module 06 - Inputs, questions & routing

Choose the route by the data the answer needs.

PDF reports provide market evidence; review CSVs provide customer language and structured attributes; sales CSVs provide exact totals and rankings. Upload them into one persistent Session (the UI name for a workspace).

One business scenario, four execution modes
ModeExample questionExecution / evidence
DIRECTWrite three taglines for a repairable speaker.General model only; no workspace data retrieved.
RAGAccording to the uploaded reports, which consumer needs matter most?Retrieve report/review passages; return source, page/section, and semantic score where applicable.
SQLWhich country has the highest total profit in the uploaded sales data?Schema-aware generation + validated read-only query; return executed SQL and result rows.
HYBRIDCombine consumer trends and sales performance to recommend a launch market.RAG and SQL in parallel; combine qualitative evidence and calculated facts before review.

Do not confuse retrieval with statistics: a bounded review overview is not a representative sample. Counts, sentiment distributions, and financial totals require SQL over stored rows, not counts inferred from retrieved passages.

Module 06 - Workflow 1 / ingest once, query repeatedly

Keep originals. Store numbers and meaning differently.

Reports → vectors

Page/section-aware text chunks, by default 400 tokens with 60-token overlap. Preserve source IDs and provenance.

Sales → SQL tables

Normalize columns and infer types across all rows. Pure financial numeric rows are stored relationally, never embedded.

Reviews → both

Keep relational rows; embed useful review text with row linkage. Skip/count blank, short, or duplicate text without removing distinct rows.

Idempotency: workspace + checksum prevents duplicate committed datasets. Failed ingestion rolls back rows/vectors and marks the document failed; original uploaded Blobs may remain and require retention cleanup.

Module 06 - Delivery, evidence & operating boundaries

Make the result inspectable. Do not overclaim the platform.

Data and SQL guardrails

Uploaded content is untrusted evidence, not instructions. Retrieval enforces workspace scope; SQL AST checks restrict tables/functions and rewrite physical tables with workspace filters, row limits, and read-only execution.

Failure and durability

Expose weak evidence and partial worker failures. Safe reads may retry once; answer revision is limited to one. Completed runs persist in agent_runs, but interrupted LangGraph workflows do not automatically resume.

Workshop, not multi-tenancy

The browser API is keyless: anyone with the Chat URL can access deployment data. The stable owner seed stays server-side; A2A uses a separate peer key. The default DB firewall allows all IPv4 sources; restrict access for production.

Preflight→storage→models→database→config→images→aca

The Bash deployment uses aca, not az containerapp sandbox or Dynamic Sessions. Auto-suspend is disabled by default for the collaborating services. Database/knowledge survives compute restarts; this is not durable in-flight scheduling.

Learning checkpoint: upload data → inspect ingestion counts → exercise all four modes → inspect citations and executed SQL → demonstrate an explicit missing-data/worker limitation. Verify real Azure connectivity and permissions; a generated manifest or process health check alone is not end-to-end acceptance.
