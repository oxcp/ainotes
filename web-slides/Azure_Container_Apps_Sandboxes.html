MAIN SCRIPT (26-minute presentation route) An agent's tool choices are not completely known when we deploy the application. During a task, it may generate Python, run a shell command, install a package, or call an API. Consider a data-analysis assistant. A user uploads a spreadsheet and asks for a chart. The assistant generates a script, imports libraries, writes temporary files, and produces an artifact. Both the generated script and its dependencies should be treated as untrusted. Running that work beside the application server creates an unnecessarily large failure domain. A bad dependency could affect the service process, its credentials, or another customer's work. Instead, the trusted application authorizes the request and delegates execution to an isolated workspace. The sandbox receives the required inputs and only the access needed for that task. The user may then disappear for five minutes and return with a follow-up question. We want to retain the working context without paying for continuous idle compute. Isolation, state preservation, and lifecycle control therefore solve different parts of one problem. None of them replaces application authorization. Next, let us see when this model is preferable to the other Container Apps options. OPTIONAL DEEP DIVE (outside the 26-minute route) Choose the isolation unit deliberately. A shared sandbox across unrelated tenants creates additional state-separation responsibilities and should not be the default design. Also distinguish resource protection from business safety: preventing one process from reaching another tenant does not determine whether an authorized user is allowed to perform a financial or administrative action through an approved API. There is also a resource-management boundary. A script can be isolated and still consume all of its assigned CPU, fill its working disk, or produce excessive output. Size the environment, bound execution time, and limit how much output the application accepts. In other words, isolation contains the workload, while the application's execution contract keeps an authorized workload useful and predictable. SLIDE 03: Choose the right Container Apps compute TIME: 2:00 (26 minutes total) TAKEAWAY: Choose sandboxes when individual workspace state and lifecycle control are part of your application. SPEAKER SCRIPT PRESENTER CUE (not spoken) Compare the four rows. Emphasize that the distinction is the application's unit of work, not a hierarchy of better services. MAIN SCRIPT (26-minute presentation route) Container Apps offers several execution models. The right choice depends on what your application needs to manage. For an app, the unit is a service. You deploy an API, frontend, or worker and keep the service available. Durable business state normally lives in an external database or storage system. For a job, the unit is a finite task. It starts, performs the work, and completes. An overnight import or queue-triggered batch calculation fits that model. Dynamic sessions provide managed execution through a session pool. The pool handles allocation and lifecycle, and its session state is ephemeral. That can be the simpler choice when your application mainly wants to submit code and receive a result. For a sandbox, the individual environment becomes part of your application's model. Your application creates it, manages files and ports, sets policy, captures snapshots, and decides when to stop or resume it. For example, a coding agent may clone a repository, modify several files, run tests, and wait for the user to request another change. Reusing the workspace can be more useful than rebuilding it on every request. More control also means more responsibility. You now need session mappings, cleanup, concurrency handling, and retention policies. If a job already meets the requirement, adding a stateful workspace may only add complexity. The decision test is the question at the bottom: do I need to control this environment after the current request? With that distinction established, we can look at the resource architecture. OPTIONAL DEEP DIVE (outside the 26-minute route) Different compute models can coexist in one solution. An app can host the trusted API and orchestrator, a job can perform scheduled housekeeping, and sandboxes can host interactive tool execution. These are complementary responsibilities. Avoid migrating every component into a sandbox simply because the agent needs one. In particular, keep the authoritative tenant directory, session mapping, and durable business records in appropriately designed external services rather than relying on a particular sandbox remaining available. As a concrete comparison, generating a report once from an input file may fit a job. Letting a user explore that file, create intermediate results, inspect a chart, and request several modifications may justify a persistent workspace. The difference is not that one workload uses Python and the other does not. It is the lifecycle and interaction contract your application needs to preserve. The data plane, at management.azuredevcompute.io, operates the workspaces. Creating a sandbox, executing a command, transferring files, and managing snapshots or policies are data-plane activities. Inside the group, the three boxes represent independently isolated compute instances, not three processes sharing one application runtime. A practical group design might separate production from development, or workloads with different networking and identity requirements. Your application must still enforce tenant authorization within its own session model. Finally, the caller needs a Microsoft Entra identity; personal Microsoft accounts are not supported. If group creation fails, inspect the ARM request, deployment configuration, and relevant control-plane permissions. If the group exists but command execution fails, inspect the data-plane principal, role scope, group selection, and request details. Do not solve every access failure by granting subscription-wide permissions. For automation, distinguish the identity calling the sandbox API from an identity a sandbox may use to reach a downstream service. Those are different permission relationships. For example, the orchestrator might be allowed to create and execute a workspace, while the workspace's downstream access is restricted to reading one approved data source. Neither permission relationship should imply unrestricted access to the other. When reviewing the architecture, draw these identities as separate arrows and record the role scope on each arrow. Container Apps offers several execution models. The right choice depends on what your application needs to manage.

MAIN SCRIPT (26-minute presentation route)

There are three security layers here, and they address different risks.

First is execution isolation. A sandbox is a hardware-isolated microVM with its own Linux kernel and virtual hardware. Unlike an ordinary container process sharing its host kernel, the workload executes against its own guest kernel. That provides a stronger containment boundary, not a guarantee that every action inside it is safe.

Second is destination control. The detailed egress guide states that a sandbox without an egress policy has unrestricted outbound access. Having a proxy in the architecture does not mean a restrictive policy is already active.

For untrusted execution, configure a Deny default when creating the sandbox and allow only the endpoints the task requires.

Also distinguish proxy injection from environment variables. A secret placed in the sandbox's environment can be read by code running there.

The complete design therefore combines isolation, restrictive networking, narrowly scoped credentials, and business authorization.

Next, we will separate private networking from those authorization controls.

MAIN SCRIPT (26-minute presentation route)

Private networking answers two separate questions. Can my application reach the sandbox service privately? And can a sandbox reach my private resources?

The central distinction on this slide is that stopping compute is not the same as deleting the environment.

First, identity. Verify the caller's Entra identity and data-plane role. Keep tenant authorization in the trusted application. Give downstream identities only the permissions the task requires.

Second, networking. Set the egress policy at creation. Prove that a required request succeeds and an unapproved request is denied. If private connectivity is involved, verify DNS, routing, and destination authorization independently. Expose inbound ports only when necessary.

Third, state. Choose the suspend mode intentionally. Test what survives a stop, a resume, and a deletion. Separate reusable baselines from tenant data, and define retention and backup for persistent storage.

Fourth, operations. Configure telemetry from the beginning. Check core quota and API-rate limits. Test concurrency, cancellation, throttling, and recovery from uncertain execution results. Measure end-to-end readiness rather than quoting startup capability as an application SLA.

Fifth, geography. Choose a supported region that meets latency and residency requirements. Sandbox groups are regional, and the current guide says snapshots are not portable across regions. A multi-region application therefore needs its own recovery and data strategy.

For the first pilot, include a complete lifecycle: create, execute, stop, resume, inspect telemetry, and clean up. Add one denied network request and one restored-state check. A successful echo command alone does not validate the architecture.

The three takeaways are the same ones we started with: isolate execution, preserve useful state, and keep application control.

Sandboxes provide the execution boundary and lifecycle primitives. Your application remains responsible for authorization, orchestration, and the business meaning of the work.

OPTIONAL DEEP DIVE (outside the 26-minute route)

A useful pilot acceptance matrix includes positive and negative cases. Can the correct tenant resume its workspace, and is another tenant rejected? Does an approved API work, and is an unapproved destination blocked? Does disk state return after stopping, and does the application recover when an external token has expired? Can abandoned sandboxes and their retained data be identified and cleaned up? Define these outcomes before the pilot so that success means more than creating an environment through the portal.

For recovery, decide which data is authoritative and how it can be reconstructed in another region. A clean environment image may be redeployable, while a captured session snapshot is not a cross-region recovery strategy under the current documented limitations. Define acceptable recovery time and acceptable data loss for the application, then test the external data and workspace reconstruction process against those requirements. Do not let a convenient resume experience substitute for a disaster-recovery plan.

在认定一个设计已经具备生产就绪条件之前，请用真实工作负载逐项通过这五个关卡。

第一，标识。验证调用方的 Entra 标识和数据平面角色，把租户授权保留在可信应用中，并且只给下游标识授予任务真正需要的权限。

第二，网络。创建环境时就设置出站策略。既要验证必需请求能够成功，也要验证未经批准的请求确实被拒绝。如果涉及私有连接，应分别验证 DNS、路由和目标授权。只有确实需要时，才暴露入站端口。

第三，状态。明确选择挂起模式，测试停止、恢复和删除后分别能保留什么。把可复用基线与租户数据分开，并为持久化存储定义保留和备份策略。

第四，运维。从一开始就配置遥测，检查内核配额和 API 请求速率限制，并测试并发、取消、限流，以及执行结果不确定时的恢复。要测量端到端的就绪时间，而不是把平台启动能力当作应用 SLA。

第五，地域。选择支持该服务、且满足延迟和数据驻留要求的区域。沙箱组是区域性资源，当前指南说明快照不能跨区域迁移。因此，多区域应用需要自行设计恢复和数据策略。

第一个试点应覆盖完整生命周期：创建、执行、停止、恢复、检查遥测，以及清理。还应包含一次被拒绝的网络请求和一次状态恢复验证。只成功执行一条 echo 命令，并不能验证整个架构。

最后记住的三点，和开场时一致：隔离执行，保留有价值的状态，并把应用控制权掌握在自己手中。

Sandboxes 提供执行边界和生命周期原语；授权、编排，以及任务在业务上的意义，仍然由应用负责。

可选深讲（不计入约 26 分钟主讲路线）

一个有用的试点验收矩阵，应该同时包含正向和反向案例：正确的租户能否恢复自己的工作区，其他租户是否会被拒绝？获准访问的 API 能否正常调用，未经批准的目标是否会被拦截？停止后磁盘状态能否恢复，外部令牌过期时应用是否能正常恢复工作？能否识别并清理废弃沙箱及其保留数据？应在试点开始前定义这些结果，让成功不再只是“在门户里创建了一个环境”。

对于恢复，还要明确哪些数据是权威数据，以及如何在另一个区域重建。干净的环境镜像可能可以重新部署，但根据当前文档限制，会话快照并不能作为跨区域恢复方案。应为应用定义可接受的恢复时间和数据丢失量，并验证外部数据及工作区重建流程是否达到这些要求。不要用方便的恢复会话体验，替代完整的灾难恢复计划。
