把改进送回真实业务。

“仅出站”，
说的是哪一条连接？

分别检查控制台访问、客户端入口、集群管理和数据访问，才是完整网络设计。

人先连接管理平台。

通过控制台、CLI 或 SDK 管理工作负载。现有 Microsoft Entra 凭据负责认证，平台 RBAC 负责授权。

集群主动轮询并上报健康与遥测。无需为 Anyscale 直连节点开放入站防火墙；仍需允许文档要求的 HTTPS 443 出站域名。

AKS ↔ Azure 存储 / 镜像仓库

网络可达，身份也要被允许。

06 / IDENTITY IS NOT ONE THING

把人的权限，
与程序的权限分开。

Entra ID 解决“你是谁”；平台角色与托管身份分别决定“你能做什么”和“程序能访问什么”。

01 用户身份

Entra ID + Azure RBAC

使用现有凭据登录，显式授予 Anyscale 平台角色。

Reader：只读与控制台访问
Contributor：工作负载读写
Administrator：平台管理操作*

02 平台组件

Operator 托管身份

供 Operator 在客户 Azure 环境中执行所需操作。

与用户登录和工作负载身份不同。门户在创建 Cloud 时配置相关资源与授权。

03 工作负载

Cluster 托管身份

默认由工作负载共享，可按用户、项目或任务类型细分映射。

最小权限 · 存储 / Registry 等资源访问

* Administrator 含专属 dataAction，目前管理能力仅在订阅作用域有效。不要假定 Azure Owner / Contributor 自动具备全部 Anyscale 权限。云注册另需租户内服务主体。

安装者的高权限，不应成为团队日常运行的默认权限。
本页最容易混淆的是三类主体：登录的用户、Operator 托管身份、Cluster 托管身份。 平台 Reader 至少提供控制台资源访问，工作负载读写一般分配 Platform Contributor。管理员角色还有专门的 dataAction，而 Azure Owner / Contributor 的空 dataActions 列表并不授予该操作。 一次性创建的云注册服务主体是另一件事，不属于这两个托管身份。

08 / WHERE IT FITS

不只是 Serving。
从最有价值的一段开始。

选择一个场景，观察 CPU、GPU 与分布式编排如何协作。

DATA PIPELINE

让异构处理连成一条管线。

图像、视频、文本与传感器数据，往往同时需要 CPU 解码与 GPU 模型处理。

CPU 解码→GPU 特征提取→数据集

关注：数据供给速度、跨阶段等待、输出质量。

BATCH INFERENCE

把离线吞吐，变成可测量的价值。

分布式预处理与 GPU 推理协作，批量生成向量或预测结果。通常是边界清晰的试点起点。

读取 / 分片→模型推理→向量 / 预测

关注：记录 / 秒、元 / 百万条有效记录、显存与批大小。

DISTRIBUTED TRAINING

扩展训练，也要验证恢复。

通过多节点、多 GPU 组织训练与微调。数据加载、通信、checkpoint 和中断恢复共同决定端到端效率。

数据供给→多 GPU 训练→Checkpoint

关注：达到目标质量的时间与总成本，而非只看单步吞吐。

COMPOSITE SERVING

一个服务，组合多个模型。

用 Ray Serve 编排预处理、多个模型和后处理，形成可扩展的在线应用。

请求→模型 A / B→响应

关注：尾延迟、并发、更新策略，以及服务对应的容量边界。

LLM POST-TRAINING

协调一次训练里的多个系统。

并行 Rollout、奖励评分与参数更新，让推理与训练围绕同一个目标协同。

Rollout→Reward→Training

关注：各阶段供需平衡与模型质量；不限定必须使用 RLlib。

PHYSICAL AI

让仿真环境并行起来。

调度大量独立仿真环境，收集轨迹并衔接训练。实际并发规模取决于资源需求与容量。

并行环境→轨迹收集→策略训练

关注：每条有效轨迹成本、并发伸缩与恢复语义。

场景映射，不替代框架兼容、GPU 驱动和部署验证。
按听众背景选择两到三个场景，不必逐一展开。 对于首次采用的团队，Embedding 或批量推理更容易固定数据集、建立成本基线并控制业务风险。 对训练与强化学习，要测达到相同质量所付出的总成本。对 Serving，要增加延迟与可用性目标。场景可行并不代表每个开源框架版本均已验证兼容。

10 / GET TO A VERIFIED CLOUD

先把环境验证通过，
再把模型搬进来。

推荐从 Azure 门户注册已有 AKS；自动化部署可参考官方 ARM / Terraform 路径。

  1. 准备订阅与租户

    安装权限、云注册服务主体、所需资源提供程序。

  2. 准备 AKS 与计算容量

    OIDC + Workload Identity；确认区域、SKU、vCPU / GPU 配额。

  3. 在 Azure 门户创建 Cloud

    关联 AKS，配置存储与身份，安装 Operator 扩展。

  4. 分配角色，安装与配置入口

    Anyscale 平台角色 + Envoy Gateway；配置 Operator 的 Gateway 参数。

  5. 验证 Cloud，再提交工作负载

    先检查连通性、身份与路由，再验证业务程序。

deployment gate
anyscale cloud verify --id <cloud-id>

服务区域可用 ≠ 所需 GPU SKU 可用

Operator 已安装 ≠ 客户端入口可访问

13 / READ THE BOUNDARIES

“托管”，
不等于“所有事情都包办”。

使用 Azure 专属文档判断能力范围，不直接套用通用 Anyscale 功能清单。

01

主部署路径是 AKS

VM stack 与 Anyscale-hosted clouds 不可用。客户仍负责 AKS 配置、入口控制器以及应用与数据治理。

02

Azure 管资源，Anyscale 管运行

Cloud 生命周期通过 Azure 管理；不支持通用 anyscale cloud setup / register / delete。运行、重试与回滚使用 Console / CLI。

03

多资源，不是一个跨区大集群

Cloud 可挂多个 Cloud Resource；单个 Ray 集群不跨资源调度或扩缩。Services 仅运行于 primary resource。

04

通用功能并非全部可用

不支持 Lineage tracking、Job queues 等。调度优先级用于 Jobs / Workspaces，非 Services；部分账单与预算组织设置不可用。

ARM / Resource Graph 对 tracked 与 proxied 资源的覆盖不同；Azure Policy 应按资源类型验证。故障先走 Azure Support，Microsoft 初诊并按需协调 Anyscale。

支持文档提供 Enterprise tier SLA 信息；具体指标以正式条款为准。
微软文档与 GA 公告对跨区域和多资源的描述粒度不同，不能把跨资源容量管理理解为单个 Ray 集群跨区扩展。 Cloud 和 Cloud Resource 是 ARM tracked 资源；许多工作负载为 proxied 资源，虽然可从门户父 Cloud 导航访问，但不在标准 ARM 清单中。 资源归属、软件维护与故障支持是不同责任维度；Operator 软件由 Anyscale 维护，但运行在客户 AKS 中。
